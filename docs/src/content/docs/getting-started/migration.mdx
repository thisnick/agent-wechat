---
title: Migration to the Native Runtime
description: Move from the official-client container to a native daemon on the host or in Docker.
---

The previous setup required a Docker container running both the official WeChat Linux app and the UI-control server. The new `wx` executable communicates directly with WeChat. Its daemon can run **on the host or in a native-only container**; the CLI connects to either through the same authenticated API.

This is a major release. The old UI server/image, `wx-legacy`, and Wechaty puppet/gateway integrations are retired from the new distribution. Existing containers, images, volumes and published older versions are preserved. Marking the historical public puppet package deprecated in npm is a separate release-administration step.

## Profile paths and platform compatibility

The current daemon and writable profile integration support **Linux x64/ARM64 and the validated Linux profile family**. The CLI does not ship a macOS or Windows executable. OpenClaw on another OS can connect in external mode to a supported Linux daemon.

| Official installation | Location / selection | Current takeover status |
| --- | --- | --- |
| Linux | Bare `--official` searches the daemon user's HOME for `xwechat_files`; an explicit path can select a complete HOME, `xwechat_files`, or its active account directory | Supported for the validated layout; account and every encrypted database must pass admission |
| macOS | Observed location: `~/Library/Containers/com.tencent.xinWeChat/Data/Documents/xwechat_files/` | Path recorded; database, saved-login, encryption and write compatibility are unverified |
| Windows | Read the configured data location in WeChat; do not assume a fixed drive or user Documents path | Discovery and profile takeover are unverified |

The macOS folder's visible `all_users` and account (`wxid_…`) directories resemble Linux's shared/account split. Inside a compatible account directory, `db_storage` holds databases and separate directories hold media. This top-level resemblance is not a schema/version or saved-device compatibility check. Names such as `Backup` and `old_backup` do not establish that a directory is a complete, consistent operating profile.

That macOS location is an application data directory; pointing to it does **not** request a copy. `--official` always attaches in place on the **daemon host**. A Linux container cannot resolve a macOS host path until the operator makes it available at a container mount path, and mounting or copying it does not convert the format. Protected macOS files also require the host application's OS permission; the daemon does not grant or bypass that permission.

Copying a stopped, complete profile into a separate working directory is a separate, explicit choice. Existing experimental copy/import commands preserve bytes; they do not translate macOS/Windows databases, re-create saved trust, or validate cross-platform takeover. macOS-to-Linux import and writeback must be tested on a preserved copy before support can be claimed. The current migration instructions below apply to a supported **Linux** source profile, including the old official-client container.

## What changes

| Existing setup | Native setup |
| --- | --- |
| Official app and UI server must run in Docker | `wx serve` runs directly on Linux or in the optional native container |
| CLI connects to the container's old `/api` | CLI connects by URL/token to the daemon's `/v1`, on the host or in Docker |
| Official HOME/profile lives in a bind mount or named volume | Keep using that stopped profile in place, or use a complete stopped copy |
| Agent database contains old server sessions, keys and job metadata | New `dataDir` holds native registry, protected credentials, journals and jobs separately |
| `wx up/down`, UI screenshots, chat selection and VNC | `wx serve`, `wx daemon start/status/stop`, native history and message operations |
| OpenClaw uses `serverUrl` and inline `token` | OpenClaw uses `native` managed/external hosting and an environment/SecretRef token |
| Read local history through the running official app's files | Read supported official files through native snapshots; continue supported writes directly |

Linux x64 and ARM64 with glibc 2.36+ are supported distribution targets. The native image includes FFmpeg/FFprobe; direct installs need those tools for outbound audio/video preparation. See [requirements](/hosting/requirements/) and [installation](/getting-started/cli/installation/).

## Preserve the existing profile

First identify the old container and its actual mounts:

```bash
docker inspect OLD_CONTAINER --format '{{json .Mounts}}'
```

Settle or record any uncertain sends/jobs before handoff. Stop the old container/app, then preserve a consistent backup of its complete official HOME/profile and old agent state. Do not remove its volumes. The relevant official tree includes both `xwechat_files` and `.xwechat`, including saved device/login information and regional settings. The old `agent.db` alone is not this profile, and it is not the native daemon's registry.

For an existing bind mount, its host source can remain the operating profile. For a named volume, mount that volume explicitly into the new native container, or prepare a complete stopped copy for a host daemon. A copy is optional: **an import is unnecessary when taking over existing files in place**. Preserve the original and its backup.

Choose one native process owner and give its OS user legitimate read/write access to the selected profile and separate native data/scratch paths. The example image uses UID/GID 10001; an older profile may have a different owner. Plan permissions or a matching service user explicitly rather than recursively changing an existing profile's ownership without review.

Do not run the old official app and the native daemon against the same profile simultaneously. Ownership leases protect cooperating native processes; they cannot prevent someone reopening the official app.

## Option A: run the daemon on the host

Install the exact native release, then start the daemon:

```bash
wx serve
```

In another terminal under the same OS user:

```bash
wx auth login --official=/absolute/stopped-official-home
wx accounts list
wx --account ACCOUNT_ID messages list filehelper --limit 5
```

Use the daemon account ID returned by `accounts list`; do not assume an old container session ID is the same identifier. `--official` selects files on the **daemon host**, binds their saved identity and uses them in place. It does not copy or launch the official app.

The defaults keep settings in `~/.config/agent-wechat/server/config.toml` and additional native data in `~/.local/share/agent-wechat`. A directly attached official profile remains at its selected path. To choose a different data root, use the default server configuration file:

```toml
schemaVersion = 1
listen = "127.0.0.1:6174"
dataDir = "/absolute/native-data"
```

The default owner API token is created as `dataDir/api-token`, separately from WeChat credentials. A CLI using the same default settings can find it; another client needs an explicit endpoint/token reference. See [storage](/operations/data/) and [tokens](/operations/tokens/).

After verification, choose foreground `serve`, `wx daemon`, the optional systemd user unit, or OpenClaw managed hosting as the process owner. Use one of these owners at a time. Stopping the daemon retains reusable saved trust; it does not submit native logout.

## Option B: keep a server container

Use the new [native Compose example](/hosting/docker-compose/), which runs the standalone daemon without the official app, X11 or VNC. Provision its native data/scratch volumes and private API token as described there. Its versioned image supports `linux/amd64` and `linux/arm64`.

Add the existing profile explicitly. For an old **named volume**, add an additional volume entry and declare it external in the reviewed native Compose configuration:

```yaml
services:
  agent-wechat-native:
    volumes:
      - existing-official-home:/profiles/wechat

volumes:
  existing-official-home:
    external: true
    name: YOUR_EXISTING_HOME_VOLUME
```

Replace the volume name with the one identified from the old container. `external: true` requires the existing volume instead of silently creating an empty replacement. For a **host directory**, add this bind entry instead:

```yaml
- type: bind
  source: /absolute/stopped-official-home
  target: /profiles/wechat
  bind:
    create_host_path: false
```

These are additions to the native example, not complete deployment files. Review permissions and the final configuration before starting the new owner. Keep the official profile separate from `/var/lib/agent-wechat` (native data) and `/var/cache/agent-wechat` (disposable scratch).

Once the native container is running, point the host CLI at it:

```bash
wx config server add native-container --url http://127.0.0.1:6174 \
  --token-file /absolute/path/native-api-token
wx --server-name native-container auth login --official=/profiles/wechat
wx --server-name native-container accounts list
wx --server-name native-container --account ACCOUNT_ID messages list filehelper --limit 5
```

The CLI's token file is on the **CLI host** and contains the matching native API token. `/profiles/wechat` is inside the **server container**. The CLI can stay on the host or another machine; it does not need to run a local daemon. For cross-host access, use verified HTTPS or an authenticated encrypted tunnel to the loopback listener.

## Login and client configuration

Keep the profile's username, UIN, full device identity and saved login/key information together. Native login attempts usable saved trust first; WeChat may still require phone approval or a fresh white-background QR. Successful authentication must match the selected account and unlock every selected encrypted database before writes begin. A fresh QR does not bypass an account/database mismatch.

Old `/api` consumers need migration to native `/v1`; this is not a URL-only swap. Use native resource IDs, scoped tokens, durable send/job IDs, idempotency keys and cursor semantics. Registered routes do not imply every network operation is supported. See the [API reference](/reference/api/) and [CLI workflows](/getting-started/cli/commands/).

For OpenClaw, external hosting works with **either** the host daemon or the native container:

```json
{
  "channels": {
    "agent-wechat": {
      "enabled": true,
      "dmPolicy": "disabled",
      "groupPolicy": "disabled",
      "native": {
        "mode": "external",
        "accountId": "ACCOUNT_ID",
        "endpoint": "http://127.0.0.1:6174",
        "token": { "source": "env", "provider": "default", "id": "AGENT_WECHAT_TOKEN" },
        "consumerStateDir": "/absolute/openclaw-wechat-consumer",
        "readPolicy": "never"
      }
    }
  }
}
```

Supply the same daemon API token through the Gateway environment or a configured OpenClaw secret provider; see [token references](/integrations/openclaw/configuration/#api-token-references). The plugin creates no token file. Remove `native.tokenFile` if migrating an earlier native configuration.

Remove old `serverUrl`, inline `token`, `pollIntervalMs` and `authPollIntervalMs` settings. Reapply the intended sender allowlists, group/mention policies and read policy after verification. The consumer directory holds new native custody/read receipts; do not substitute the old server database for it. If OpenClaw should own the local daemon instead, use [managed mode](/integrations/openclaw/setup/) after stopping the other native owner. It requires an independently provisioned executable and native data directory.

## Verify and retain a recovery path

Check native account status, existing history, contact/group lookup and cached media before changing the old setup. Reading history does not send messages or mark them read. Whole-thread marking reports its read boundary across devices. Server sync does not fetch every historical thread.

The supported workflow continues official-format database/media writes in place and preserves unknown files. FTS/search-index maintenance, arbitrary official-schema migration and universal reverse handoff are not promised. Unknown sync commands remain staged instead of advancing a falsely complete official checkpoint. Inspect uncertain sends by their retained key/job; do not replay them as new messages during migration.

Retain the stopped old profile/agent backup and the new native data root. If reverting, stop the native owner and preserve its current state first. Returning native-written files to the official app is an experimental extra; use a known compatible consistent backup for a deliberate old-stack recovery rather than mixing individual database files or sharing a live writer.

Proxy configuration from the old container is removed; native outbound proxy support is a follow-up. Wechaty integrations are retired. The native profile remains official format, while experimental import/export operations copy that format rather than convert schemas.
