Everything the CLI and the OpenClaw plugin do goes through this API, so another agent framework, a bot or an app can do the same. The daemon serves JSON at `http://127.0.0.1:6174/v1`. Every request except `GET /health` needs a bearer token; create one with [`wx tokens create`](/reference/tokens/).

A typical integration follows the [event stream](#receive) for new messages, fetches each one, and replies through [`/sends`](#send).

```bash
export WX=http://127.0.0.1:6174/v1 TOKEN=...   # and ACCOUNT=<id from /v1/accounts>
curl -H "Authorization: Bearer $TOKEN" $WX/accounts
```

## Profiles

Use the existing daemon connection key for profile management. There is no separate
frontend role to configure.

| Action | Request |
| --- | --- |
| List profiles | `GET /accounts` |
| Add a profile | `POST /accounts` with `{ "alias": "Personal" }` |
| Sign in | `POST /accounts/{id}/login-attempts` with an `Idempotency-Key` |
| Sign out | `POST /accounts/{id}/auth/logout` with an `Idempotency-Key` |
| Remove a signed-out profile | `DELETE /accounts/{id}` with `{ "confirmAccountId": "<same id>" }` |

Removal returns `{ "accountId": "…", "removed": true, "filesRetained": true }`.
It unregisters the profile and keeps its local files and recovery records. Sign out
and wait for active operations to finish first; otherwise the response is `409`.
Removed IDs and profile paths stay reserved. The existing token scopes apply:
creation, renaming and removal use `admin`; sign-in and sign-out use `login`.

## Read

```bash
curl -H "Authorization: Bearer $TOKEN" "$WX/accounts/$ACCOUNT/threads?limit=20"
curl -H "Authorization: Bearer $TOKEN" "$WX/accounts/$ACCOUNT/threads/filehelper/messages?limit=50"
curl -H "Authorization: Bearer $TOKEN" "$WX/accounts/$ACCOUNT/messages?query=invoice"
```

Lists return `{ "items": [...], "nextCursor": "..." }`. Pass `cursor=` with the same query to get the next page.

Contact, thread, group and member reads include [peer classification](/use/contacts/)
from saved WeChat metadata. It keeps entity category separate from conversation
`kind` and contact `relation`.

`GET /threads` and `GET /threads/{id}` include sidebar summaries from saved history:

| Field | Contents |
| --- | --- |
| `muted` | Saved notification preference for a direct chat or group: `true`, `false`, or `null` when missing or unresolved. |
| `pinned` | Saved pin state for an ordinary direct chat or active group: `true`, `false`, or `null` when unavailable. |
| `lastMessage` | Latest local message ID, sender ID/name, direction, type, time and a plain-text `text` preview of up to 160 characters. `null` means empty local history; omitted means the preview is unavailable. |
| `avatarMembers` | Up to four cached group members, each with `id` and `displayName`; empty for direct chats or an unavailable roster. Fetch cached pictures through `GET /avatars/{username}`. |

These reads do not refresh WeChat or download media. Media messages use labels such as “Photo” and “Sticker”; recalled content stays suppressed. Refresh the thread list after message, contact or group events to update the summaries. Phone contact changes arrive through the independent contact sync stream. For a manual refresh, use `POST /contacts/{id}/refresh` and wait for the operation to finish. Notification consumers should require account status `contactSyncReady: true` and thread `muted: false` before alerting. Notification edits through `PUT /threads/{id}/notifications` support ordinary direct contacts and groups. A direct edit reads the current contact before submitting its change. Repeat the same idempotency key to recover an operation; an uncertain outcome must not be resubmitted with a new key.

Pin or unpin with `PUT /threads/{id}/pin`, body `{"pinned":true}` or `{"pinned":false}`, an `admin` token and `Idempotency-Key`. The SDK method is `setThreadPinned(accountId, threadId, pinned, key)`. The response is an operation; inspect its `remoteOutcome` and `profileProjection`. Saved pin changes emit `thread.updated`; refetch the thread or list. A new list places pinned chats first, then orders each section by saved activity. An existing pagination cursor keeps its original order.

## Send

```bash
curl -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -H "Idempotency-Key: order-1234-confirmation" \
  -d '{"threadId": "filehelper", "text": "Order 1234 confirmed"}' \
  "$WX/accounts/$ACCOUNT/sends"
```

Every send needs an `Idempotency-Key`. Sending the same key again returns the original send instead of sending twice. Check progress with `GET /sends/{id}`, or find a send by key with `GET /sends/by-idempotency-key?key=...`.

To quote a saved message, send both its `id` and `serverId` from that chat's message list:

```json
{
  "kind": "text",
  "threadId": "filehelper",
  "text": "Agreed",
  "quote": { "messageId": "MESSAGE_ID", "serverId": "SERVER_ID" }
}
```

The token needs `read` and `send`. The daemon reads the original from the same chat; callers supply only its IDs. In the TypeScript SDK:

```ts
await client.sendText(accountId, threadId, "Agreed", key, { messageId, serverId });
```

See [quoted replies in the CLI guide](/use/cli/#quoted-replies) for supported originals and limits.

For files, images, video and voice, stage bytes with `POST /uploads` and send the returned source ID. [Send attachments](/use/media/) covers the request, SDK methods, per-kind capability limits and longer job polling.

## Receive

```bash
curl -N -H "Authorization: Bearer $TOKEN" "$WX/accounts/$ACCOUNT/events/stream"
```

A server-sent event stream. A new message arrives as a `message.committed` event; fetch it with `GET /messages/{messageId}`. To resume after a disconnect, reconnect with `?after=CURSOR` (or the standard `Last-Event-ID` header) and the daemon replays what you missed. `POST /consumers/{name}/ack` with `{"cursor": "..."}` records how far you've processed.

The stream sends an immediate heartbeat comment, followed by periodic keepalives.
Heartbeat comments contain no message and do not advance the event cursor.

Recognized group changes emit `group.updated` after the saved profile changes; fetch `GET /groups/{groupId}` or its members. `group.refresh_blocked` means a follow-up read could not finish. These events share the same replayable stream. Automatic delivery of every edit made on another device is not established; see [group refresh limits](/use/groups/).

## Routes

All account routes start with `/v1/accounts/{account}`.

| Area | Routes |
| --- | --- |
| Accounts | `GET /v1/accounts`, `GET /`, `GET /capabilities`, `POST /connect`, `POST /disconnect`, `POST /logout` |
| Login | `POST /login-attempts`, `GET /login-attempts/{id}`, `GET /login-attempts/{id}/qr`, `POST /login-attempts/{id}/cancel` |
| Chats and messages | `GET /threads`, `GET /threads/{id}/messages`, `GET /messages?query=`, `GET /messages/{id}` |
| Contacts and groups | `GET /contacts`, `GET /groups`, `GET /groups/{id}`, `GET /groups/{id}/members`, `GET /groups/{id}/members/{username}`, `POST /contacts/lookup` |
| [Group edits](/use/groups/) and chat settings (admin) | `POST /groups`, `PATCH /groups/{id}`, `POST /groups/{id}/leave`, `POST/DELETE /groups/{id}/members`, `PUT /groups/{id}/my-name`, `DELETE /groups/{id}/announcement`, `PUT /threads/{id}/notifications`, `PUT /threads/{id}/pin` |
| Sending | `POST /uploads`, `POST /sends`, `GET /sends/{id}`, `POST /sends/{id}/cancel`, `POST /messages/{id}/recall` |
| Media | `GET /messages/{id}/media`, `POST /media/lookup`, `POST /messages/{id}/media-transfers`, `GET /media/{id}/content` |
| Read state | `POST /threads/{id}/read-state` with `{"expectedVersion": "..."}` |
| Background work | `GET /jobs/{id}`, `GET /operations/{id}` |
| Events | `GET /events`, `GET /events/stream`, `POST /consumers/{name}/ack` |
| Tokens | `GET /v1/tokens`, `POST /v1/tokens`, `DELETE /v1/tokens/{id}` |

Request and response types are generated from the Rust source into [`native.generated.ts`](https://github.com/thisnick/agent-wechat/blob/main/packages/shared/src/native.generated.ts). The [`wechat-api`](https://github.com/thisnick/agent-wechat/tree/main/packages/native-client-rust/crates/wechat-api) crate is the source of truth.

To read attachment metadata together, send `{"messageIds":["MESSAGE_ID_1","MESSAGE_ID_2"]}`
to `POST /media/lookup` with the `media` scope. A batch accepts up to 40 message IDs
and returns an `items` array with each `messageId`, its `assets` and an `error`
code or `null`. It does not download attachments. In the SDK, use
`client.mediaAssetsBatch(accountId, messageIds)`.

<Aside title="Good to know">
- **IDs are strings.** Message IDs are opaque, and server IDs can exceed JavaScript's safe integer range. Don't parse them as numbers.
- **Long work returns 202** with a job or operation ID: media sends, downloads, recalls, logins. Poll it; closing the request doesn't cancel it.
- **`needs_review` means unknown, not failed.** WeChat may have accepted it. Look it up; don't resend.
- **Media downloads** can return `pending`, `expired` or `unsupported`. Cached files keep working after WeChat's copy expires, and content routes support `Range` requests.
- **Read state and acks are separate.** Acknowledging an event never marks a message read.
- **Remote access:** the daemon listens on localhost only. Use HTTPS or a tunnel.
- The 0.x container's `/api` is gone. `/v1` uses different routes and IDs.
</Aside>
