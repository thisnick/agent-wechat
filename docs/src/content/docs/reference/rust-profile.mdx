Use `wechat-profile` to read or update supported official WeChat profile files.
Its job is to understand the existing storage formats and preserve unrelated
data. Network operations, account policy and application recovery belong to the
caller. The library does not supply an alternative database for settled history.

## Read a profile

1. Stop the profile's writer or supply a consistent copy.
2. Load your protected `KeyFile` and open `ProfileReader`, as shown in
   [Rust libraries](/reference/rust-libraries/#read-a-stopped-profile).
3. Use its history, contacts, groups and cached-media queries. Reading a cached
   attachment never starts a download.

An application that already owns the live profile can use `OwnedReaderCache`
with its own synchronization. Setting an ownership or snapshot flag does not
stop another process.

## Understand the writer names

The prefixes describe this implementation's operations. They are not names from
an official WeChat API, and they do not define separate transaction levels.

| Prefix | Usual meaning | Example |
| --- | --- | --- |
| `stage_*` | Prepare bytes without changing the profile | `stage_mmkv_values` |
| `apply_*` | Write a logical record update | `apply_message_projection` |
| `publish_*` | Install bytes at local profile paths | `publish_mmkv_append`, `publish_cache_file` |

Both `apply_*` and `publish_*` write data. The convention has exceptions:
`publish_saved_key_info` can update both a database and a legacy file, and media
apply operations can install files. Read each operation's contract rather than
inferring atomicity from its prefix.

New profile mutations use `apply_*`; existing `publish_*` names remain for
compatibility. `stage_*` continues to mean preparing a change without writing it.

"Prepared bytes" means new file contents already constructed and checked. For
example, an MMKV update works like this:

1. Read the existing encrypted data and `.crc` metadata.
2. `stage_mmkv_values` constructs the updated encrypted data and matching CRC
   metadata in memory, retaining unrelated keys.
3. The caller saves the information needed to recover an interrupted update.
4. `publish_mmkv_append` writes temporary files, flushes them and replaces the
   profile's data file, then its metadata file. It checks the expected previous
   contents and recognizes an already completed update.

Here, publication means making bytes available at their final **local** paths.
It does not upload a file, publish a crate or send a WeChat message.

## Keep format work separate from coordination

The public API currently includes recovery-oriented hooks such as
`WriteOptions::durable_intent_id`. This references a recovery record the caller
already saved. The crate checks the supplied reference but cannot prove the
record exists. It does not create the daemon's journal, send queue or account
authorization policy.

The guiding boundary is to implement supported official storage behavior.
Staging, expected-content checks and replay support help an application write
those files safely; they do not establish that the official client uses the
same transaction or recovery implementation.

<Aside title="Good to know">
Writers require exclusive profile access, matching keys/account identity and a
supported schema. A database transaction or atomic file replacement does not
make several databases and files one atomic operation. The caller owns recovery
before committing its sync cursor. Support for the selected Linux layout does
not establish compatibility with official Windows or macOS profiles.
</Aside>
