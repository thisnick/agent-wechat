Use [`NativeClient`](https://docs.rs/wechat-protocol/1.3.0/wechat_protocol/struct.NativeClient.html)
to call supported WeChat server operations. Most operations are methods on this
type, so they appear under its **Methods** section rather than the crate's
top-level Functions list.

| Layer | Responsibility |
| --- | --- |
| `NativeClient` and protocol modules | Authenticated transport, requests and response decoding |
| `AccountState` | Secret credentials and account routing, updated by responses |
| Your application | Credential storage, send recovery, sync handling and profile writes |

The daemon's native upstream adapter calls this same protocol library. Some
operations combine a request builder, a client RPC and a decoder instead of a
single convenience method. CDN transfers use the crate's `media` module.

## Send one text message

1. Add `wechat-protocol` using [Rust libraries](/reference/rust-libraries/).

2. Obtain `AccountState` from phone-approved login: call `start_qr_login`, display
   the returned QR privately, poll until `LoginStatus::Approved`, then call
   `complete_login`. Keep credentials in memory or an encrypted application store.

3. Submit with the recipient's exact WeChat username. This function takes the
   timestamp and task ID your application saved before the send:

   ```rust
   use wechat_protocol::{wire, AccountState, NativeClient, TextSendResult};

   fn send_once(
       client: &NativeClient,
       state: &mut AccountState,
       recipient: &str,
       text: &str,
       task_id: &str,
       created_at: u32,
   ) -> anyhow::Result<TextSendResult> {
       let client_id = wire::client_message_id(task_id.as_bytes());
       anyhow::ensure!(client_id != 0, "Choose another task ID");
       client.send_text(state, recipient, text, created_at, client_id)
   }
   ```

4. Check `accepted`, `returned_destination_matches` and
   `returned_client_id_matches`. A successful receipt includes a decimal-string
   `server_message_id`. It establishes server acceptance; the caller still owns
   history writeback and handling an uncertain outcome.

## Run the source examples

From a repository checkout:

```bash
cargo run --manifest-path packages/native-client-rust/Cargo.toml -p wechat-protocol --example send_text -- RECIPIENT UNIQUE_TASK_ID "Hello from the Rust example"
```

The program prints a private QR image path to open. After phone approval, it
submits once and prints a receipt such as:

```json
{
  "accepted": true,
  "outer_code": 0,
  "item_code": 0,
  "server_message_id": "1234567890123456789",
  "returned_destination_matches": true,
  "returned_client_id_matches": true
}
```

The message ID above is illustrative. The other examples are `qr_login` (login
only), `sync_once` (one sync-page summary), and `protobuf` (a local codec example).
Network examples keep credentials in memory and never write an official profile.
`--help` makes no network requests.

For a persistent receiver, handle and retain the returned sync commands before
committing the next cursor. Unknown command payloads remain available for later
handling. `sync_once` is a preview and saves no checkpoint.

<Aside title="Good to know">
Network calls block; async callers should use a blocking worker. The examples
request fresh device logins, so use a test account; login may replace another
active desktop session. Text requires an exact username, not a display name.
An I/O error after submission can mean the server accepted the message. A client
ID does not guarantee deduplication; investigate before submitting again.
</Aside>
