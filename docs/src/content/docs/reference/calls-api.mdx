Use the control WebSocket for call commands and events. Its winning owner can
attach the separate [JSON PCM media socket](../calls-media/).
[Rust crate architecture](../../how-it-works/rust-crates/) explains package responsibilities.

## Routes and snapshot

All routes require an account-authorized `calls` bearer token in the
`Authorization` header, including WebSocket upgrades. URL-encode identifiers;
never put credentials in URLs.

| Method | Path | Response |
| --- | --- | --- |
| GET | `/v1/accounts/{account}/calls/current` | JSON snapshot |
| WebSocket | `/v1/accounts/{account}/calls/socket` | JSON control messages |
| WebSocket | `/v1/accounts/{account}/calls/{callId}/media` | Versioned JSON and base64 PCM |

```bash
curl -sS -H "Authorization: Bearer $TOKEN" \
  "$BASE/v1/accounts/$ACCOUNT/calls/current"
```

```json
{
  "conferenceInvitations": [{
    "invitationId": "invitation-example",
    "revision": 1,
    "groupId": "group@chatroom",
    "callerId": "contact-a"
  }],
  "capabilities": {
    "directAudio": true,
    "conferenceCreate": true,
    "conferenceJoin": true,
    "conferenceInvite": true,
    "conferenceAudio": true
  },
  "availability": {
    "busy": false,
    "ownedByThisClient": false
  },
  "currentOffer": null,
  "currentPendingOffer": null,
  "currentCall": null,
  "audioFormat": {
    "sampleRate": 16000,
    "channels": 1,
    "frameMs": 20
  }
}
```

| Field | Meaning |
| --- | --- |
| `capabilities` | Available flags only; missing flags mean unavailable; `{}` means no calling |
| `conferenceInvitations` | Fresh opaque invitation IDs/revisions, group and caller; no room credentials |
| `currentPendingOffer` | Incoming candidate waiting for readiness or preparation; cannot be answered |
| `currentOffer` | Actionable incoming offer; clears when claimed or ended |
| `currentCall` | Active call metadata, including kind, type, state, conference roster or reported direct-call controls |
| `audioFormat` | Client/daemon PCM format, independent of the WeChat codec |

Reported conference participants include `participantId`, `contactId` and
`membership` (`joined`, `invited`, `left` or `unknown`). When the server supplies microphone state, `microphoneEnabled` is
`true` or `false`; an omitted value means unknown. Muting a microphone does not
remove the participant from the room.

Same-account observers see call metadata without owner tokens or audio access.
HTTP ownership is always false: ownership belongs to a control socket.
`busy` is scoped to this account, including any unresolved call outcome that
blocks a new call. Each account has its own call controller.

## Conference commands

1. Check `conferenceCreate`, `conferenceJoin`, `conferenceInvite` and
   `conferenceAudio` for the operation you need. Advertise outgoing
   [readiness](#readiness) before creating or joining.
2. To create a call, supply the group ID and between 1 and 100 contact IDs:

   ```json
   {
     "type": "call.dial",
     "requestId": "create-1",
     "target": {
       "kind": "conference",
       "groupId": "group@chatroom",
       "invitees": ["contact-a", "contact-b"]
     },
     "callType": "voice"
   }
   ```

   To join an existing call instead, select an entry from `conferenceInvitations`
   and send its exact ID and revision:

   ```json
   {
     "type": "call.join",
     "requestId": "join-1",
     "invitationId": "invitation-example",
     "invitationRevision": 1
   }
   ```

   A stale, withdrawn or already used invitation is rejected with `offer_expired`.
   Joining never creates a replacement room. Conference invitations use
   `call.join`, rather than the direct-call `call.answer` command.
3. Keep the owning socket open. Creation and joining return a `command.result`
   with the call ID and owner token; wait for `call.state` to become `connected`.
   To invite more contacts after connection, send:

   ```json
   {
     "type": "call.invite",
     "requestId": "invite-1",
     "callId": "example-conference",
     "contactIds": ["contact-c", "contact-d"]
   }
   ```

`call.invitation_result` reports each initial or later invitation separately;
it does not mean the contact joined. `participant.updated` reports membership
and microphone changes. `call.mute` changes our microphone; `call.hangup` leaves
our membership without ending the other participants' call.
A leave remains valid across roster changes for the same owned call. Repeating
it while it is ending does not submit another leave operation. A confirmed
prior removal completes locally; an unconfirmed result stays uncertain.
Check the reported capabilities before submitting commands. Direct-to-conference
promotion is unavailable in this version.

## Protocol version

Within five seconds of opening the control socket, announce supported versions:

```json
{"type": "call.hello", "supportedProtocolVersions": [2]}
```

Wait for the server's `hello` and check `protocolVersion` before sending commands.
The daemon supports version 2 only. An omitted announcement means version 1;
there is no compatibility fallback. A mismatch returns this before closing with
WebSocket code 1002:

```json
{"type":"protocol.error","code":"unsupported_protocol_version","clientVersions":[1],"serverVersions":[2]}
```

Empty, null, duplicate or malformed version lists return
`invalid_protocol_version`. The CLI and OpenClaw plugin announce version 2 and
reject an unsupported server. Media attachment negotiates independently.

## Client messages

Send these JSON text messages on the **control** socket. After the version announcement, every command has a
`requestId`; reuse it only for an identical command. Use the latest received
revision for answer/reject/cancel/hangup. Example revisions below are illustrative.

### Readiness

Prepare your audio path, then advertise readiness. Connecting alone stays passive.

```json
{
  "type": "call.ready",
  "requestId": "ready-outgoing",
  "ready": true,
  "format": {
    "sampleRate": 16000,
    "channels": 1,
    "frameMs": 20
  },
  "scope": {
    "kind": "outgoing"
  }
}
```

Ready for one pending incoming call:

```json
{
  "type": "call.ready",
  "requestId": "ready-offer",
  "ready": true,
  "format": {
    "sampleRate": 16000,
    "channels": 1,
    "frameMs": 20
  },
  "scope": {
    "kind": "offer",
    "callId": "example-call",
    "expectedRevision": 1
  }
}
```

Ready for incoming and outgoing calls, or withdraw readiness:

```json
{
  "type": "call.ready",
  "requestId": "ready-all",
  "ready": true,
  "format": {
    "sampleRate": 16000,
    "channels": 1,
    "frameMs": 20
  },
  "scope": {
    "kind": "all"
  }
}
```

```json
{
  "type": "call.ready",
  "requestId": "not-ready",
  "ready": false,
  "format": {
    "sampleRate": 16000,
    "channels": 1,
    "frameMs": 20
  }
}
```

Omitting `scope` means `all`.

### Start or answer

```json
{
  "type": "call.dial",
  "requestId": "dial-1",
  "target": {
    "kind": "direct",
    "contactId": "example-contact"
  },
  "callType": "voice"
}
```

```json
{
  "type": "call.answer",
  "requestId": "answer-1",
  "callId": "example-call",
  "expectedRevision": 3
}
```

The initiating socket owns an outgoing call. For incoming calls, the first
successful answer wins; competing clients receive `already_claimed`.

### Reject, cancel or hang up

Reject an incoming offer, cancel your outgoing call before pickup, or hang up
after answering/connecting:

```json
{
  "type": "call.reject",
  "requestId": "reject-1",
  "callId": "example-call",
  "expectedRevision": 3
}
```

```json
{
  "type": "call.cancel",
  "requestId": "cancel-1",
  "callId": "example-call",
  "expectedRevision": 4
}
```

```json
{
  "type": "call.hangup",
  "requestId": "hangup-1",
  "callId": "example-call",
  "expectedRevision": 5
}
```

### Audio controls

Mute outgoing audio; send `muted: false` to unmute. Clear queued outgoing audio
when interrupting a response; see [stream generations](../calls-media/#mute-and-interrupt).
`call.mute` silences this client's outgoing stream in the daemon. For a conference,
it also requests our room microphone state. It does not control another
participant's microphone. A mute change clears queued audio and advances the
send generation, just as `call.clear_audio` does.

```json
{
  "type": "call.mute",
  "requestId": "mute-1",
  "callId": "example-call",
  "muted": true
}
```

```json
{
  "type": "call.clear_audio",
  "requestId": "clear-1",
  "callId": "example-call"
}
```

## Server messages

These JSON text messages arrive on the **control** socket. Media attachment has
its own [`media.ready` response](../calls-media/#attach-and-exchange-audio).

### Hello

The first event includes the connection's `clientId` and a current snapshot:

```json
{
  "type": "hello",
  "protocolVersion": 2,
  "clientId": "example-client",
  "conferenceInvitations": [{
    "invitationId": "invitation-example",
    "revision": 1,
    "groupId": "group@chatroom",
    "callerId": "contact-a"
  }],
  "capabilities": {
    "directAudio": true,
    "conferenceCreate": true,
    "conferenceJoin": true,
    "conferenceInvite": true,
    "conferenceAudio": true
  },
  "availability": {
    "busy": false,
    "ownedByThisClient": false
  },
  "currentOffer": null,
  "currentPendingOffer": null,
  "currentCall": null,
  "audioFormat": {
    "sampleRate": 16000,
    "channels": 1,
    "frameMs": 20
  }
}
```

### Conference invitations and results

`conference.invitations` replaces the current invitation list. An empty array
clears it; invitation IDs are account-specific and contain no room credentials.

```json
{
  "type": "conference.invitations",
  "invitations": [{
    "invitationId": "invitation-example",
    "revision": 1,
    "groupId": "group@chatroom",
    "callerId": "contact-a"
  }]
}
```

The owner receives per-contact results linked to the create or invite command's
`requestId`. For example, the later `invite-1` command can produce:

```json
{
  "type": "call.invitation_result",
  "callId": "example-conference",
  "requestId": "invite-1",
  "results": [
    {
      "contactId": "contact-c",
      "status": "submitted",
      "serviceCode": 0,
      "verificationRequired": false
    },
    {
      "contactId": "contact-d",
      "status": "unknown",
      "verificationRequired": false
    }
  ]
}
```

| Status | Meaning |
| --- | --- |
| `submitted` | The service accepted the invitation submission |
| `rejected` | The submission was rejected |
| `unknown` | No per-contact service result was supplied |
| `uncertain` | The operation may have reached the service; do not retry automatically |

`serviceCode` is omitted when unavailable. `verificationRequired: true` reports
that the service requested verification; the event does not contain a verification
URL or complete that step. Invitation results are separate from room membership.

### Command results

Match `requestId` to your command. Readiness succeeds without claiming a call:

```json
{
  "type": "command.result",
  "requestId": "ready-outgoing",
  "status": "accepted",
  "callId": null,
  "ownerToken": null,
  "code": null
}
```

A successful claim includes a secret token for media attachment:

```json
{
  "type": "command.result",
  "requestId": "dial-1",
  "status": "accepted",
  "callId": "example-call",
  "ownerToken": "<secret owner token>",
  "code": null
}
```

Conference creation and joining claim ownership in the same way. A successful
`join-1` response is:

```json
{
  "type": "command.result",
  "requestId": "join-1",
  "status": "accepted",
  "callId": "example-conference",
  "ownerToken": "<secret owner token>",
  "code": null
}
```

Acceptance starts the operation; it does not mean connected. An identical request
can return `replayed`. A rejected command returns `error` and a fixed code:

```json
{
  "type": "command.result",
  "requestId": "ready-outgoing",
  "status": "replayed",
  "callId": null,
  "ownerToken": null,
  "code": null
}
```

```json
{
  "type": "command.result",
  "requestId": "answer-1",
  "status": "error",
  "callId": null,
  "ownerToken": null,
  "code": "already_claimed"
}
```

### Pending and actionable offers

A pending candidate has phase `waiting_for_ready` or `preparing`:

```json
{
  "type": "call.pending",
  "offer": {
    "callId": "example-call",
    "revision": 1,
    "kind": "direct",
    "callType": "voice",
    "callerId": "example-contact",
    "phase": "waiting_for_ready"
  }
}
```

```json
{
  "type": "call.pending",
  "offer": null
}
```

An actionable offer can be answered or rejected using its revision:

```json
{
  "type": "call.offered",
  "offer": {
    "callId": "example-call",
    "revision": 3,
    "kind": "direct",
    "callType": "voice",
    "callerId": "example-contact"
  }
}
```

### State and availability

Conference state includes a group and the latest roster. Here `contact-a` has no
reported microphone state; `contact-b` is still joined with its microphone off:

```json
{
  "type": "call.state",
  "call": {
    "callId": "example-conference",
    "revision": 5,
    "kind": "conference",
    "callType": "voice",
    "direction": "outgoing",
    "state": "connected",
    "ownedByThisClient": true,
    "groupId": "group@chatroom",
    "participants": [
      {"participantId": "member-4", "contactId": "contact-a", "membership": "joined"},
      {"participantId": "member-5", "contactId": "contact-b", "membership": "joined", "microphoneEnabled": false}
    ]
  }
}
```

Roster changes advance the call revision and emit `participant.updated` to
same-account clients, followed by the updated call snapshot:

```json
{
  "type": "participant.updated",
  "callId": "example-conference",
  "revision": 6,
  "participant": {
    "participantId": "member-5",
    "contactId": "contact-b",
    "membership": "left"
  }
}
```

Use the reported `participantId` for track associations; do not assume it is a
contact ID. A removed participant can emit `membership: "left"` while disappearing
from the snapshot's current roster.

A direct call continues to use this shape:

```json
{
  "type": "call.state",
  "call": {
    "callId": "example-call",
    "revision": 5,
    "kind": "direct",
    "callType": "voice",
    "direction": "incoming",
    "state": "connected",
    "ownedByThisClient": true,
    "controls": [
      {
        "participantId": "example-contact",
        "control": {
          "kind": "microphone",
          "muted": false
        }
      }
    ]
  }
}
```

```json
{
  "type": "call.state",
  "call": {
    "callId": "example-call",
    "revision": 6,
    "kind": "direct",
    "callType": "voice",
    "direction": "incoming",
    "state": "ending",
    "ownedByThisClient": true
  }
}
```

```json
{
  "type": "call.state",
  "call": {
    "callId": "example-call",
    "revision": 7,
    "kind": "direct",
    "callType": "voice",
    "direction": "incoming",
    "state": "ended",
    "ownedByThisClient": true
  }
}
```

```json
{
  "type": "calls.availability",
  "availability": {
    "busy": false,
    "ownedByThisClient": false
  }
}
```

States are `offered`, `dialing`, `ringing`, `connecting`, `connected`, `ending`,
`ended` and `uncertain`. Stop audio at `ending`; keep control connected while the
daemon finishes cleanup. `uncertain` reports an unconfirmed backend outcome;
its network receipts are retained even when the local session closes.

### Participant control events

For direct calls, `call.control` reports a participant's control state. The current
control kind is `microphone`; `muted: true` means muted, and `false` means unmuted. `participantId`
is the contact ID used by the direct-call target or incoming offer.

```json
{
  "type": "call.control",
  "callId": "example-call",
  "participantId": "example-contact",
  "control": {
    "kind": "microphone",
    "muted": true
  }
}
```

```json
{
  "type": "call.control",
  "callId": "example-call",
  "participantId": "example-contact",
  "control": {
    "kind": "microphone",
    "muted": false
  }
}
```

These events go to the owner and same-account observers. They need no reply;
clients can ignore them. Repeated unchanged microphone state produces no event.
The latest known values also appear in `currentCall.controls` in HTTP snapshots,
`hello` and `call.state`. An omitted `controls` means no state has been reported.
Control updates do not change the call-state revision or PCM format, end the call,
or interrupt audio in the other direction.
Conference microphone changes appear in `participants` and `participant.updated`;
an omitted `microphoneEnabled` is unknown, not `false`.

### Audio generation and errors

After successful `call.clear_audio` or a mute change, the send track advances:

```json
{
  "type": "track.updated",
  "callId": "example-call",
  "track": {
    "id": 1,
    "generation": 2,
    "direction": "send",
    "format": {
      "sampleRate": 16000,
      "channels": 1,
      "frameMs": 20
    }
  }
}
```

Receive-track `track.added` and `track.removed` examples and their ordering with
audio are in the [media reference](../calls-media/#receive-tracks-and-timing).

A socket-level failure uses `call.error`:

```json
{
  "type": "call.error",
  "code": "forbidden"
}
```

Error codes are `invalid_request`, `busy`, `already_claimed`, `offer_expired`,
`not_owner`, `unsupported`, `media_not_ready`, `outcome_unknown`, `capacity`,
`stale`, `forbidden` and `closed`. Lost replies do not authorize automatic retry.

:::note[Good to know]
Reconnecting does not reclaim ownership. Control messages are limited to 16 KiB.
The server sends WebSocket Pings every 15 seconds. A connection without incoming
traffic for 60 seconds closes. Closing the owner's socket stops media and starts
call cleanup; another observer cannot keep that ownership alive. Muting or quiet
audio does not count as a lost control connection.

On daemon restart, previous calls are locally ended and `currentCall` is empty.
Old requests are never replayed. A normal shutdown first attempts call cleanup;
unconfirmed network outcomes remain recorded separately from local call state.
`kind` is `direct` or `conference`; this backend implements voice calls when the
corresponding capabilities are present. Video and direct-to-conference promotion
are unavailable. Native calls currently have a 20-minute safety limit.
:::
