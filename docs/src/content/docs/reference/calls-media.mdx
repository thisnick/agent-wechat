---
title: Call media API
description: Exchange PCM audio and encoded video as binary WXCM v3 frames on an authenticated WebSocket.
---

Send and receive PCM16 little-endian audio and H.265, H.264 or JPEG video in
binary `WXCM` v3 WebSocket frames alongside JSON track-lifecycle messages. Each
frame carries a 32-byte header with its track ID, generation, payload kind,
flags, sequence and timestamp. The daemon clocks outgoing audio, negotiates
pass-through or transcoded video codecs, and handles the WeChat connection.

Direct and conference calls tolerate authenticated receive nonce reuse for
legacy peer compatibility. The daemon counts reuse, filters duplicate packets,
and checks the protected sender before accepting media. Outgoing counters keep
their limits and require a new key generation when exhausted.

## Attach and exchange media

1. Negotiate version 3 on the [control socket](../calls-api/#protocol-version),
   claim a call, and wait for `call.state` with `state: "connected"`.
   Keep the owning control socket open.
2. Open `/v1/accounts/{account}/calls/{callId}/media` with either the account's
   `calls` bearer token in the `Authorization` header or a single-use `?ticket=`
   minted via `POST /v1/accounts/{account}/calls/socket-ticket`. Within five
   seconds, send:

   ```json
   {
     "type": "media.attach",
     "supportedProtocolVersions": [3],
     "clientId": "example-client",
     "ownerToken": "<secret owner token>"
   }
   ```

3. Wait for `media.ready`. Directions are relative to your application.
   `sendTracks` and `receiveTracks` are arrays containing audio tracks and, on
   video calls, video tracks.

   ```json
   {
     "type": "media.ready",
     "protocolVersion": 3,
     "sendTracks": [
       {
         "media": "audio",
         "id": 1,
         "generation": 1,
         "direction": "send",
         "format": {"sampleRate": 16000, "channels": 1, "frameMs": 20}
       },
       {
         "media": "video",
         "id": 65537,
         "generation": 1,
         "direction": "send",
         "format": {
           "codec": "h265",
           "mode": "passthrough",
           "maxWidth": 640,
           "maxHeight": 480,
           "maxFps": 15
         },
         "active": true
       }
     ],
     "receiveTracks": [
       {
         "media": "audio",
         "id": 2,
         "generation": 1,
         "direction": "receive",
         "format": {"sampleRate": 16000, "channels": 1, "frameMs": 20}
       },
       {
         "media": "video",
         "id": 65538,
         "generation": 1,
         "direction": "receive",
         "format": {
           "codec": "jpeg",
           "mode": "transcoded",
           "maxWidth": 640,
           "maxHeight": 480,
           "maxFps": 15
         },
         "active": true
       }
     ]
   }
   ```

4. Start each outgoing track you intend to send, then send binary `WXCM` frames:

   ```json
   {"type": "track.start", "trackId": 1, "generation": 1}
   ```

   Receiving audio or video does not require starting an outgoing track.

## Binary `WXCM` v3 frame layout

Every binary WebSocket message starts with a 32-byte little-endian header:

| Offset | Size | Field | Meaning |
| ---: | ---: | --- | --- |
| `0` | 4 | `magic` | ASCII `WXCM` (`57 58 43 4d`) |
| `4` | 1 | `version` | `3` |
| `5` | 1 | `kind` | `1` = `pcm_s16le`, `2` = `h265`, `3` = `h264`, `4` = `jpeg` |
| `6` | 2 | `flags` | Bit `0x0001` keyframe, `0x0002` codec config (VPS/SPS/PPS), bits `0x000c` clockwise rotation (`0x0000` = 0°, `0x0004` = 90°, `0x0008` = 180°, `0x000c` = 270°) |
| `8` | 4 | `trackId` | Track ID from `media.ready` / `track.added` |
| `12` | 4 | `generation` | Active track generation |
| `16` | 8 | `sequence` | Per-track monotonic frame sequence (`0` allowed on client TX) |
| `24` | 8 | `timestampMicros` | Microseconds on the track timeline (for PCM receive, `sampleOffset * 1_000_000 / 16_000`) |
| `32` | *N* | `payload` | Raw PCM16LE samples, Annex-B H.265/H.264 access unit, or standalone JPEG |

| Property | Current value |
| --- | --- |
| Audio encoding | PCM16 little-endian, 16,000 Hz mono, 20 ms daemon frames (640 bytes) |
| Max audio payload | 65,536 bytes (whole samples), at most eight seconds queued |
| Max video payload | 512 KiB per frame (`524,288` bytes) |
| Max WebSocket frame | `524,320` bytes (`32` + `512 KiB`) |
| Video codec negotiation | Pass-through first when client and wire codec match; FFmpeg transcoding fallback otherwise |

Audio chunks need not match 20 ms codec frame boundaries; the daemon combines
smaller chunks and splits larger ones.

## Receive tracks and video keyframes

With `conferenceAudio` or `conferenceVideo` available, a conference has
independent receive tracks per participant. The daemon does not mix audio
tracks. Each track carries an optional `participantId` linking it to the roster.
Sources can appear or disappear during a call via `track.added`, `track.updated`
and `track.removed` JSON messages on both sockets. Apply the media socket's
ordered events to its binary frames: additions precede a source's frames, and
removal stops delivery for that generation.

To request a fresh keyframe on a remote receive video track (for example after a
local decoder reset), send on the media socket:

```json
{"type": "video.request_keyframe", "trackId": 65538}
```

When the remote peer requests a keyframe from your outgoing camera stream, the
daemon emits on the media socket:

```json
{"type": "video.keyframe_requested", "callId": "example-call", "trackId": 65537, "generation": 1}
```

## Mute, camera toggle and interrupt

Send `call.mute`, `call.camera` or `call.clear_audio` through the control
socket. Changing mute or clearing audio emits `track.updated` with the audio
send track's new generation; toggling the camera emits `track.updated` with the
video send track's new generation and `active` flag:

```json
{
  "type": "track.updated",
  "callId": "example-call",
  "track": {
    "media": "video",
    "id": 65537,
    "generation": 2,
    "direction": "send",
    "format": {
      "codec": "h265",
      "mode": "passthrough",
      "maxWidth": 640,
      "maxHeight": 480,
      "maxFps": 15
    },
    "active": false
  }
}
```

Stop the old producer, send `track.start` for the new generation when active,
then send fresh `WXCM` frames. Old-generation frames are discarded; future or
unknown track IDs are rejected.

## Good to know

- Omitting `supportedProtocolVersions` means version 1. This daemon supports
  version 3 only and returns `protocol.error` before closing with code 1002.
  An empty, null or malformed list is invalid.
- Check `directVideo` / `conferenceVideo` and `videoCapabilities` before
  advertising video codecs in `call.ready`. Screen sharing and
  direct-to-conference promotion are unavailable. Native calls currently have a
  20-minute safety limit.
- Video rotation flags (`0x000c` mask) convey clockwise display rotation so
  receivers can rotate decoded frames without restarting the daemon's video
  decoder.
- Audio and video queue overruns keep recent incoming frames. A slow control
  consumer closes its connection. Losing the owning control connection starts
  call cleanup.
