```text
~/.config/agent-wechat/
├── server/config.toml              daemon settings (optional)
└── client.toml                     CLI: saved servers and default account
~/.local/share/agent-wechat/        data folder
├── api-token                       owner API token
└── accounts/<id>/
    ├── profile/                    WeChat profile: history, contacts, media
    └── agent/
        ├── control.sqlite          credentials, jobs, event log
        └── media/                  encrypted attachment and upload files
$TMPDIR                             offline inspection snapshots
```

On Windows, settings live in `%APPDATA%\agent-wechat` and data in `%LOCALAPPDATA%\agent-wechat`. macOS uses the same paths as Linux.

If you logged in with `--official`, there's no `profile/` folder: the daemon uses WeChat for Linux's `~/xwechat_files` and `~/.xwechat` where they are, and keeps only its own files in the data folder.

## Where attachments are kept

| Attachment | Kept in |
| --- | --- |
| Images, files, videos and voice notes | The WeChat profile only. The daemon reads them from there. |
| Stickers, link thumbnails, images and stickers inside a quoted message | `agent/media/`, one encrypted file each. The profile has no place for them. |
| Files staged for sending | `agent/media/`, until a day after every send that used them has finished. |

If you delete an attachment's file, fetching that attachment returns `media_not_cached`. The daemon doesn't download it again by itself.

## How `control.sqlite` stays small

`control.sqlite` holds work in progress, not history: queued sends, sync batches waiting to be written to the profile, and receipts that stop a request from running twice. The daemon cleans it up when it starts and then every hour. Cleanup only removes bytes the daemon already owns. It never sends, downloads or changes the profile.

| Record | Kept in full while | Then |
| --- | --- | --- |
| Received message batches | waiting, or among the newest 256 | only the batch ID is kept, for 30 days |
| Blocked message batches | among the newest 256 | only the commands not yet written, plus contact records |
| Text and media sends | unfinished, or not yet in the profile, plus a day | a short receipt, for 90 days |
| Sticker jobs (packs, Saved stickers, sends, pack downloads) | unfinished, or not yet in the profile, plus a day | a short receipt; the newest five downloads of each pack keep what adding the pack again needs to reuse the file |
| Voice note audio | until the profile holds the same audio | read from the profile |
| Group and contact changes, recalls | unfinished, or not yet in the profile, plus a day | a short receipt, for 365 days |
| Duplicate checks for messages and events | 30 days | removed |
| Raw WeChat replies kept for troubleshooting | 7 days | removed |
| Attachments never downloaded, except voice notes | 7 days, or while a download is queued | removed; listing the message's media again brings them back |

A request with an unknown outcome (`needs_review`) keeps its full record for 7 days, or until 100 newer ones pile up. After that, sends and media jobs stay `needs_review`, and group and contact changes and recalls become `expired` with the code `review_expired`. Either way it can no longer be repaired automatically. See [Sends and recovery](/how-it-works/sends/#how-long-a-key-works).

Freed space goes back to the disk. To see what is using space, stop the daemon and run:

```bash
wx store usage --account ID
```

It lists the file size, the largest tables and `runtime` key families, and unfinished work that cleanup has to keep.

## Back up

Stop the daemon (`wx daemon stop`, `systemctl --user stop agent-wechat-native` or `docker compose stop`), then copy the data folder:

```bash
tar -czf wechat-backup.tgz -C ~ .local/share/agent-wechat
```

With `--official`, add `xwechat_files .xwechat` to that command. The profile alone would lose queued sends, OpenClaw's progress and recall records; the data folder alone would have no history.

## Change locations

Set `dataDir` in `~/.config/agent-wechat/server/config.toml`, or pass `--data-dir`. See [Configuration](/reference/configuration/).

<Aside title="Good to know">
- **The running daemon reads its owned profile directly.** It reuses read-only database connections and short read transactions. Offline inspection uses private database copies (up to 2 GiB each, 8 GiB in total), so keep `$TMPDIR` on a disk with room, and never point it at the profile.
- **Unknown profile formats aren't touched.** The daemon checks each database's layout before writing, and stops if it doesn't recognize it. Back up and wait for an update rather than forcing it.
- **Damaged databases are kept.** If the daemon's own database fails a check, it keeps the original files and a recovery copy alongside.
- **Starting can leave temporary copies.** Before opening a database that needs an upgrade or wasn't closed cleanly, the daemon checks a copy in a `.sqlite-admission-*` folder beside it. If the daemon is stopped during that check, the folder stays until that database next opens successfully, and is then removed.
- **Older data folders are converted after start.** Earlier versions kept every attachment inside `control.sqlite`. The daemon moves them out in the background, deletes files nothing refers to, and then shrinks the database. Until that finishes, the folder can briefly need extra space for the attachments the profile doesn't hold.
- **Back up before upgrading.** An upgrade can change the data folder's format, and an older `wx` can't open a folder a newer one has upgraded. After that, cleanup permanently removes finished records from `control.sqlite`. To go back to an older version, restore the backup you made before upgrading.
- **Recall markers live in the data folder.** A profile export doesn't include them.
- **The first cleanup after upgrading can take a while.** It works in small steps, so other requests keep running. Removing the first large batch needs free disk space about twice the size of `control.sqlite`; without it the space is reclaimed later.
- **Blocked sync batches are kept.** A batch with a command the daemon doesn't support stays until a later version can write it to the profile, and the profile's saved sync position waits for it. `wx store usage` counts them under `syncBatchesBlocked` and lists the status and system controls that block them under `blockedControls`.
- **`wx store usage` upgrades the data folder** to the installed version's format, like any other `wx store` command. Run it on a copy if you want to keep the original as it is.
- OpenClaw keeps its own progress in `consumerStateDir`. Back that up too. After an upgrade from an earlier plugin release, the first start converts that file to the new format and keeps the original beside it, ending in `.v1-backup`. The backup still holds message text; delete it once you no longer need to go back. An older plugin can't read the converted file; restoring the backup to go back makes it handle again the messages that arrived since the upgrade.
</Aside>
