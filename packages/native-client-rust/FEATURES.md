# Native client implementation checklist

This checklist tracks implementation and validation separately. A command or
route appearing in help is not evidence of a successful native exchange. The
supported-profile runtime has explicit compatibility limits. The initial scope is taking over an existing
stopped official profile, using its saved identity and continuing supported
database/media writes in place. Fresh-profile creation, export and returning the
store to the official app are outside this scope.
No deployment or package publication is part of this implementation task.

Legend: **Implemented** means executable code and focused tests exist;
**Partial** identifies an unfinished required behavior; **Pending** identifies
work still required. Live validation is stated separately and never inferred
from fixture tests. Capability responses must reflect these limits.

## History performance checks

Ordinary workspace tests check the amount of history work without depending on
runner speed:

- Quote normalization keeps using its captured snapshot when the source becomes
  unavailable, while still checking current recall receipts.
- ID-only membership matches full message ordering across shards, timestamp
  ties and multiple pages, and rejects the existing history capacity limit.
- Off-page bodies larger than the reader's value limit do not prevent loading
  page one. Requesting those bodies still reports an error.
- Search retains normalized content matching. Continuations preserve their
  original membership while resolving later recalls from fresh profile state.
- Paused request-owned reads retain the same database and event boundary while
  another read and the single writer advance. Exhausted pools queue before the
  writer; failures return their connections. Rollback profiles remain serialized.
- Two paused incoming image downloads can overlap independently of the send
  queue, while history reads and writer events still complete. A third download
  waits; cancellation and logout prevent late results from becoming available.
  Sync/contact/heartbeat network waits also release the writer and retain their
  credential-state checks. These fixtures do not establish live server behavior.
- Thread lists, chat history and cached media responses include `Server-Timing`
  durations for the read queue, account wait, blocking-worker queue, snapshot and
  query, plus the parallel/serialized mode. The header contains no account IDs,
  paths, SQL, message content or credentials. Media discovery still registers
  existing local files under the writer; content reads reuse the owned reader
  instead of copying the entire profile for each asset.

For a latency gate, use a quiet release builder with temporary files on the
filesystem being measured:

```bash
cargo +1.93.1 test --release --locked \
  --manifest-path packages/native-client-rust/Cargo.toml \
  -p wechat-core history_latency_benchmark -- --ignored --nocapture
```

This local-only synthetic benchmark creates an encrypted profile with 2,002
messages, including quoted replies whose original is outside the first page.
After one warmup, it reports p50/p95 for 20 first-page reads in each scope
(one chat and the account). Its default p95 budget is 100 ms; set
`WECHAT_HISTORY_P95_MS` to an agreed budget for a different builder. Timing is
opt-in so noisy shared CI cannot produce false failures. This measures core
history reads, including snapshot capture and saved cursors; HTTP/CLI overhead
and larger profiles require separate measurement. Content search still scans
normalized history and does not have the same latency claim.

## Release gate

Before describing an initial capability as complete, exercise its actual daemon
API and CLI, retain a reproducible fixture or controlled test receipt, verify
restarts and failure paths, and update this table. User-visible playback and
phone approval remain distinct from a successful server response. Current local
artifacts are validation inputs, not a published or deployed release.

### Desktop notification and update validation

Native desktop listeners consume SSE for authenticated accounts on the selected hub. Installed macOS/Windows notification acceptance remains separate.
