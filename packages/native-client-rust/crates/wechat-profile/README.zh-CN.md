# wechat-profile

[English](README.md) | [简体中文](README.zh-CN.md)

读取和更新受支持的官方 Profile 文件。查询操作推荐使用 `ProfileReader`；安全检查的写入器服务于独占拥有该 Profile 的应用程序。格式适配器完整遵循受支持的微信存储行为规范。集成该库的应用自行负责网络操作、账号策略和崩溃恢复。

`stage_*` 负责在内存中准备数据，不改变物理文件。`apply_*` 与 `publish_*` 均会执行写入操作：前者通常表示逻辑记录更新，后者通常表示将数据安装到本地路径。这些命名并不定义不同的事务级别。例如，`publish_saved_key_info` 可以同时更新数据库和一个旧式文件。MMKV 更新首先在内存中暂存新的加密数据及匹配的 CRC 元数据，随后将这些数据发布到既有的 Profile 路径中，不涉及任何服务端上传。

新的 Profile 变更推荐使用 `apply_*`。既有的 `publish_*` API 保留其名称以维持向下兼容。

现有的公共 API 还公开了协调钩子，如 `WriteOptions::durable_intent_id`。这是对调用方先前保存的持久化恢复记录的引用；该库会检查传入的引用，但无法证明该记录确实存在或外部进程已停止。这些钩子并不增加新的官方 Profile 格式，也不直接提供守护进程的恢复日志。

有关 API 边界和写入阶段术语的详细说明，请参见 [Rust 开发库指南](https://thisnick.github.io/agent-wechat/zh-cn/reference/rust-libraries/#profile-写入操作)。

## 读取已停止的 Profile

`wechat-profile` 用于读取显式指定的、已停止运行的 Linux 微信账号 Profile。它在没有官方可执行文件、Agent 服务端、网络连接或原生登录的情况下运行。它不负责破解密码，也不从运行中的进程内存中获取数据。

```rust,no_run
use wechat_profile::{KeyFile, ListQuery, ProfileLocation, ProfileReader, ReadOptions};
# fn main() -> wechat_profile::Result<()> {
let location = ProfileLocation::new("/private/account")?;
let keys = KeyFile::load("/private/keys/profile.keys.json")?;
let reader = ProfileReader::open(location, keys, ReadOptions {
    stopped_or_consistent_snapshot: true,
    ..Default::default()
})?;
let first = reader.contacts(&ListQuery::default())?;
# Ok(()) }
```

选择包含 `db_storage` 的单一账号根目录，或该目录本身。包含多个账号的完整 HOME 目录需要由调用方显式选择具体账号。密钥文件中的 `accountBinding` 绑定了目录名和文件加盐值；它并不向微信认证该账号。网络写入需要独立验证的已认证用户名绑定。

每次数据库查询都会打开私有的临时 main/WAL/SHM 副本。SQLite 绝不直接打开原始源路径。双重清单和 SHA-256 扫描会检测复制过程中发生修改或新增的文件。这**不是**实时的跨文件快照算法：调用方必须停止写入者或提供一致的快照。直连模式和托管复制模式具有相同的所有权要求。仅靠 SQLite 的只读/不可变（immutable）标志并不能保证运行中 WAL 快照的一致性。

读取器会发现每个实际的普通/业务消息分片并使用其自身的 `Name2Id`；本地消息 ID 包含相对数据库路径和表名。原始 SQLite 字段保留 NULL、作为十进制字符串的有符号 64 位整数、BLOB、非法的 UTF-8 TEXT、压缩标志和未知列。服务器 ID 展现完整的无符号 64 位十进制表示。联系人/成员目录保留缓存的系统、官方、群组和成员行；它们不是好友总数统计。群成员身份通过保留的 Protobuf 成员身份进行核验。

列表限制为 1–200。不透明的本地游标绑定了所选快照代际、查询条件和完整的排序元组（包括跨分片关系）。它们不是 API Token、守护进程事件游标或原生 SyncKey。发生改变的源代际会使翻页游标过期，而不是混合不同快照的数据。Zstandard 解压、SQLite BLOB 大小、查询耗时、源大小/数量以及元数据解析均具有明确的限制。架构指纹使用定义、列、索引和触发器。SQLite 的 schema counter 属于诊断信息，不是官方发布版本号。自定义 FTS 虚表保持被清点状态，但其分词器行为不受支持。

## 密钥与本地多媒体

版本 1 的私有 JSON 密钥文件采用如下结构（占位符数值不可作为实际密钥）：

```json
{
  "schemaVersion": 1,
  "format": "official-linux",
  "accountBinding": "selected-account-directory",
  "sqlcipher": {
    "compatibility": 4,
    "pageSize": 4096,
    "kdfIterations": 256000
  },
  "databases": [
    {
      "relativePath": "contact/contact.db",
      "saltHex": "<16 字节十六进制>",
      "rawPageKeyBase64": "<32 字节原始 Base64>"
    }
  ],
  "imageDat": {
    "formatVersion": 2,
    "rawAes128KeyBase64": "<16 字节原始 Base64>",
    "xorByte": 0
  }
}
```

`KeyFile::load` 要求仅所有者可读写的常规文件。机密数据实现了遮蔽的 Debug，并在释放时清零。`write_new` 要求私有父目录并以原子方式发布新的 0600 文件，绝不输出到 stdout 或直接覆盖文件。调用 CLI 还必须拒绝在官方 Profile 内部输出密钥。

`keys_from_password` 接受显式提供的现有 32 字节账号密码，使用文档记录的 SQLCipher-4 参数针对每个已发现文件的 Salt 进行派生，验证首页 HMAC 和架构打开状态，且仅返回单文件密钥。这不是密码破解或全逻辑页审计。`keys_from_agent_cache` 使用现有的解锁令牌从显式选择的 Agent 数据库的一次性一致副本中读取选定的密钥记录；它绝不调用初始化器、迁移器、服务端或提取辅助工具。存在多个缓存会话时需要显式选择。缺失的缓存条目保持为差距。可用的 `_image_aes` 加 `_image_xor` 密钥对会被单独归一化。`ImageDatKey::derive(uin, username)` 实现了调研的原生规则：小写 MD5（无符号十进制 UIN 拼接用户名）的前 16 个 ASCII 字节，结合原生的 UIN 位移/异或选择器。这独立于 SQLCipher 密码，且不向网络认证账号。

缓存的头像为 SQLCipher 内部经校验的原始 JPEG/PNG 二进制 BLOB。编码后的语音字节保留其媒体分片命名空间。V2 DAT 编解码独立保留了观察到的头部/控制/分区策略，且上限为 64 MiB。其他 DAT 版本/控制值以及低于 1024 字节明文观察到的编码策略不受支持。ECB/XOR 包装不是认证加密。

`cached_image` 通过原始内容 MD5 及其硬链接目录映射解析选定消息，拒绝有歧义的群组并验证解码后的字节。原图需要 MD5 匹配；仅凭文件名后缀是不充分的。`cached_voice` 保留编码后的语音字节。`cached_hardlink_file` 检查所请求文件/视频的 MD5 并拒绝歧义绑定。网络下载和表情 CDN 任务归守护进程管理，不属于本 Crate。

## 全新布局与显式投影

`initialize_profile` 使用调研的 Linux 4.1.13.26 架构创建 7 个加密的普通数据库。`initialize_official_home_with_login` 还会创建已知的完整 HOME 身份/全局 MMKV 记录、所选账号的 `config/login_configv2` 以及原生旧版密钥信息回退。它仅发布到全新或空的目标目录中，保留失败的暂存数据以供检查，绝不覆盖已有数据的 Profile。密码必须是服务端返回的账号数据库密码；新生成的无关密码无法解密现有 Profile。账号基本名称和图片密钥由绑定的原生身份派生。同版本的官方客户端启动/渲染测试独立于架构创建和加密重新打开测试。

通用的 `require_writable()` 暂不支持。显式的消息/会话、联系人/群组/成员、头像、媒体缓存、已保存登录和 SyncKey 投影函数要求独占所有权、账号/密钥绑定、精确受支持的架构声明以及**已持久化**的意图 ID。调用方必须持有其 Profile 租约并串行化所有账号写入。建议性文件锁无法阻止不受管的官方客户端。新增的可读列并不代表具备写入授权。

消息 ID 包括数据库/表/本地 ID；服务器 ID 保留所有 64 位。消息写入器当前需要一个普通消息分片。每个聊天的新 ID 使用 AUTOINCREMENT，同秒排序分配受限并进行冲突检查。幂等重试会比对完整的受支持数据行。原生 AddMsg 序号由外部显式提供；已接受的外发消息使用单独标识的本地挂起/确认策略，而不是虚构传入序号。消息/会话事务保留无关的草稿/选项和未读计数异常。新的可空未知字段显式初始化为 SQL NULL；此策略不作为所有原生构造器默认值的依据。

稀疏联系人更新严格区分缺失字段与显式空文本。群名单补丁映射已证明的成员身份/显示字段，保留未知的根和嵌套 Protobuf 字段，且仅在经过验证的完整群名单下才移除缺失成员。群目录条目不凭空捏造会话、群主、成员关系或完整的远程群列表。自定义原生 FTS 分词器/索引写入器不受支持；原始索引文件与备份必须予以保留。

图片缓存投影编码 V2 DAT 并为原图、标准和缩略图角色写入受支持的硬链接/资源记录。硬链接 MD5 哈希采用 ASCII MD5 字符串的原生 32 位 SuperFastHash。语音投影在绑定的媒体分片中写入编码字节。文件与视频投影将明文缓存字节和受支持的 ResourceInfo/Detail 元数据绑定到现有消息，校验长度/摘要，并拒绝未知的打包元数据。所有缓存文件的发布均具有边界、防覆盖/幂等，并与网络传输分离。这并不代表覆盖了所有媒体子类型或原版客户端界面的过渡状态。

单一 SQLite 事务无法提供跨数据库/跨文件的崩溃原子性。守护进程必须保留加密的可重放意图、对账所有行/文件，并仅在所有必需的投影完成后才发布原生游标与已提交事件。纯 Profile 导出无法携带 Sidecar 恢复状态，也无法保证已完成的保存登录代际。

`mark_read_messages` 在一次会话事务中仅移除选定的限定来源未读记录。它根据实际移除的行数扣减，并保留预先存在的计数器/列表异常、无关新消息和无关字段。重试具有幂等性。此受限写入器保留作为较早持久化意图的内部恢复原语。

`mark_read_thread` 通过冻结的服务端时间戳清除整条会话，推进 `last_clear_unread_timestamp`，并保留该时间戳之后的未读行。当会话没有更新的历史时，它还会清除列表中不存在的旧版未读计数贡献。当存在更新历史时，未知的计数贡献将被保留。草稿、会话选项和其他同伴信息均予保留；会话缺失时为空操作。它与其他写入一样需要显式所有权、账号绑定、受支持架构以及持久化意图。存储的截断点具有整秒精度。具有相同时间戳的稍后到达消息共享该边界；其单独的排序需要真实验证。服务器消息 ID 绝不通过数值排序来推断先后顺序。

守护进程的公共已读操作按本地 Profile 顺序冻结其最新的有效服务器身份和时间、检查预期版本、应用此本地投影，并单独记录一次跨设备已读通知日志。这特意包含了同一会话中较早的消息（包括未提供给模型的消息）。Profile Crate 不发起网络请求；守护进程还将此写入器用于严格识别的传入已读控制。消费者确认保持为独立操作。调用方拥有其模型交接策略、回执持久化以及并发/版本检查。

## 验证

在原生 Rust 工作区中运行 `cargo test -p wechat-profile` 和 `cargo clippy -p wechat-profile --all-targets -- -D warnings`。合成测试涵盖 SQLCipher、密钥文件保护、密钥缓存导出、WAL 保留、全分片映射、uint64 标识、游标、Zstandard 限制、架构漂移、DAT 往返、媒体绑定、稀疏投影、已保存登录 CAS/重放以及文本/已读重试/恢复。Core 测试单独演练了加密的多文件检查点与已接受凭据重启日志。单元测试不代表原版客户端启动或另一个构建/架构。

独立的禁用网络验证在授权的停止运行加密快照中打开了 20 个数据库：2,736 位联系人、104 个会话、32 个群组、2,918 条成员记录、44 个解码的缓存头像以及 2,692 条消息（无未解析对等端）。此前的 17 个明文导出版返回了相同的计数。所有 60 个源加密 main/WAL/SHM 文件和 17 个明文导出版均保留了其原始哈希。

另一个一次性加密克隆接受了一条保留的传入文本，以精确的正文/来源/完整服务器身份重新打开，重试无重复，并将确切 ID 的已读状态从 1 投影到 0，具备幂等已读重试。该验证未使用网络、官方运行时、登录或消息发送。它不是全新的官方客户端交接、全量服务端历史证明或通用多文件恢复认证。示例仅打印聚合结果；私有输入数据和密钥绝不随 Crate 一同发布。

## 存储身份

`read_mmkv_identity` 仅使用调用方提供的 16 字节格式密钥解码调研的 v4 分帧。它限制大小/记录数、校验密文 CRC、应用覆盖/删除标记语义，并读取精确的 username/UIN/device 字段。未知的版本和非零过期/标志元数据会被拒绝。CRC 不是认证；守护进程在启用写入器前会将存储的身份与其独立认证的账号进行比对，并在每次写入前重新校验。全局格式密钥必须显式提供，此处不进行自动发现。账号的 `login_configv2` 使用单独派生的账号密钥。MMKV 追加发布保留无关记录和旧密文前缀，校验 CRC/元数据代际，并支持数据优先中断后的重放。完整的数据文件扩展到下一个 4096 字节页，上限为 4 MiB；未知记录绝不压缩或丢弃。耗尽该上限将返回资源错误，并使已接受的代际挂起以待恢复。新键值对发布绝不覆盖现有的/部分外部键值对。CRC 是损坏检测，不是密码学认证。

`stage_account_sync_key` 仅针对账号 SyncKey 存储。原生 SyncKey、已接收/已应用的 Sidecar 检查点、本地分页游标和登录 Cookie 是截然不同的概念。守护进程协调器必须在任何未应用的意图期间阻塞游标推进、比对接收到的代际，并原子化地退役其加密日志与公共提交事件。

已保存登录辅助工具保留启动策略和未知设置。仅显式经服务端接受的暂存 API 才会清除桌面登出锁并可能清除 Cookie。`plan_saved_key_info` 仅记录哈希预期的代际；发布需要已知的 LoginKeyInfoTable 架构/唯一索引并写入调研的原生空 `key_md5`，同时保留无关/历史行。原生最新行选择与旧版回退保持区分。未知的权威架构属于待解决的兼容性差距，绝不授权使用旧版文件进行替换。SQLCipher 密钥、保存的登录令牌和活跃会话密钥不可互换。

协调器必须将发布日志绑定到接受的凭据代际和登出纪元，在每次持久化文件写入前重新检查围栏，随后在退役日志前验证存储结果。登出可能发生在独立的文件提交之间；该窗口保留可见的挂起日志，而不是断定可以原子回滚。导入凭据本身不代表通过验收，恢复操作不进行认证或发起网络请求。
